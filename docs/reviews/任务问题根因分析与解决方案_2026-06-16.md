## 问题 5/6/7：字幕分句质量（🔴 最严重）

### 用户观测现象
```
问题5（桌面悬浮框）：
"到了，从最黑暗的深处走到黑夜，继续倒退...从最黑暗的深处走来...从最黑暗的深处走来..."
→ 短语"从最黑暗的深处走来"反复出现，应为同一句被重复分段

问题6（Web 工作台标准字幕对比）：
用户期望（来自 fixtures/testVideo）：
  [00:00-00:04] I feel so fortunate...（4秒一句）
  [00:08-00:10] I learned so much from her（2秒一句）
  
实际输出（问题6描述）：
  [00:12] She told me that a few didn't quite meet her own mark,
          她告诉我，有几幅作品没能完全达到她自己的标准，
  [00:14] For what she wanted them to be one of the works,
          因为她想让它们成为作品之一，
  [00:17] In fact so didn't meet her mark,
          事实上，所以没有达到她的目标，

→ 12-14-17 秒三句话，语义连贯应为一句（"她告诉我有几幅作品..."），被 VAD 过度拆分

问题7：
00:08 一直到 12 秒（4秒空白）→ 12-34 秒一直有字幕（22秒持续）→ 34-46 秒空白 → ...
→ 时间跨度不合理，要么句子过长(22s)，要么停顿过长(4s/12s)
```

### 根因定位（已读代码 `pipeline.py`）

#### 根因 A：DashScope VAD 断句过于敏感
- **证据**：`realtime.py:110` 只有一个 `feed_silence(1.5s)` 手动触发接口，**无 VAD 敏感度/停顿时长配置参数**（已 grep 确认 realtime.py / config.py 无 `vad` / `silence` / `threshold` 参数）。
- **推测**：DashScope LiveTranslate 的服务端 VAD 在检测到**短暂停顿（可能 < 0.5s）即切句**，导致语义连贯的一句话（如"She told me that a few didn't quite meet her own mark"）被拆成 3 段。
- **行业对比**：讯飞、字节等竞品普遍提供 VAD 敏感度参数（如"silence_duration: 1.0s"）让用户权衡"响应快 vs 句子完整"。

#### 根因 B：管线去重过头 + 合并逻辑缺陷
- **`_collapse_source_repetition`（`pipeline.py:525-544`）**：循环 4 次去重，对 CJK（中文）与拉丁文分别塌缩。**问题 5 的"从最黑暗的深处走来"反复出现，说明去重未生效或 partial 被误判为独立句**。
- **`_merge_source_partial`（`pipeline.py:435-448`）**：判断 `current.startswith(normalized_prior)` 决定是快照/增量，**但对"既非完全前缀、又非显著增长"的 partial（如重复短语）无明确处理**，可能被当独立句。
- **推测**：DashScope 回吐的 partial 可能包含**短周期重复**（如 VAD 误切后重发前文），而管线的前缀判定未覆盖"部分重复"模式 → 导致问题 5 的循环字幕。

#### 根因 C：句级拆分条件过严
- **`_maybe_split_for_display`（`pipeline.py:652-724`）**：只在 `source_count == trans_count`（原文译文句数相等）时才按句拆分。
- **影响**：若源文被 VAD 拆成 3 句、译文因模型合并为 1 句 → 不满足相等条件 → 整段作为单个 segment 显示 → 导致**单句过长（问题 7 的 22s 持续）**。
- **行业对比**：YouTube 实时字幕、Zoom 字幕会**强制按时长拆分**（如每 8-10s 必切），即使句子未完也会分段显示 `...`（续）标记。

### 最佳方案设计

#### 方案 1：DashScope VAD 参数调整（首选，但可能受限）
- **尝试**：查 DashScope LiveTranslate 文档/API，是否有隐藏的 VAD 参数（如 `vad_threshold`、`silence_duration`、`split_on_punctuation`）。
- **若有**：在 `realtime.py _session_update_event` 配置 `vad: {silence_duration: 1.0}` 等参数，让 VAD 容忍更长停顿再切句。
- **若无**：进方案 2。

#### 方案 2：管线侧二次拆分 + 去重增强（可落地）
1. **管线侧按时长 + 标点强制切分**：
   - 在 `_maybe_split_for_display` 增逻辑：若 `source_count != trans_count` 或单句 `len(text) > 150` 字符，**强制按英文标点(`.!?`) / 中文标点(`。！？`) / 或每 10s 切分**。
   - 参考 YouTube 实时字幕逻辑：超过阈值即切，续句用 `...` 衔接。
   
2. **增强去重：识别"部分重复"模式**：
   - `_collapse_source_repetition_once` 增对**短语级重复**的检测（如"从最黑暗的深处走来"出现 ≥2 次 → 合并为一次）。
   - 用滑动窗口 Levenshtein 距离或 n-gram 相似度，而非仅前缀匹配。

3. **放宽句级拆分条件**：
   - `source_count ± 1 == trans_count` 也允许拆分（容忍 VAD 多拆/少拆 1 句）。
   - 或只要 `max(source_count, trans_count) > 1` 就尝试拆（即使不相等）。

#### 方案 3：前端降级——本地二次拆分（最稳妥但体验次优）
- 前端收到长句时（如 `endMs - startMs > 8000`），按标点 / 固定字数在展示层拆分为多行。
- 缺点：后端时间码仍不准、纠偏/报告仍按长句处理。

### 推荐执行顺序
1. **先查 DashScope 文档** → 若有 VAD 参数 → 直接配置（工作量 0.2 人天）。
2. **若无** → 实施方案 2 的"管线侧强制切分 + 去重增强"（约 1.5 人天）。
3. **测试**：用真实链路跑 fixtures/testVideo，对比终稿字幕与 en.txt/ch.txt 的句子粒度。

## 问题 2：播放/暂停快速切换 + 卡顿（🟠）

### 用户观测
点击暂停后，播放/暂停按钮快速切换，视频卡顿。

### 根因定位（已读 `MediaPanel.vue` + `session.ts`）

#### 根因 A：`suppressPauseEvent` 抑制逻辑不完整
- **`MediaPanel.vue:80-98`**：
  ```typescript
  function pauseMedia(silent = false) {
    if (element && !element.paused) {
      suppressPauseEvent = silent;  // 标记"这次 pause 不要 emit"
      element.pause();
    }
  }
  function handlePause(event: Event) {
    if (suppressPauseEvent) {     // 若标记了就跳过
      suppressPauseEvent = false;
      return;
    }
    if (!element.ended) emit("playbackPause");
  }
  ```
- **问题**：`suppressPauseEvent` 是**模块级变量**（非响应式），若 `pauseMedia` 与用户点击原生控件触发的 `handlePause` **竞态**，抑制可能失效。

#### 根因 B：`session.ts` 的 pause/play 事件处理可能触发循环
- **`session.ts:1276/1284`**：
  ```typescript
  emit("playbackPause")  → socket.send({ type: "pause_session" })
  emit("playbackPlay")   → socket.send({ type: "resume_session" })
  ```
- **推测**：若后端 `pause_session` / `resume_session` 回发某个状态事件 → 前端 `applyServerEvent` 又调用 `pauseMedia()/playMedia()` → 再次触发原生 pause/play → **循环**。
- **未读到后端对 pause/resume 的处理**（`ws.py` 接收这俩消息但可能只改内部状态），需确认是否回发事件。

#### 根因 C：AudioWorklet 采集与 video 生命周期冲突
- `MediaPanel` 同时管 video 播放 **与** AudioWorklet 采集（经 `useAudioCapture` 的 `startMediaElementAudioCapture`）。
- **推测**：pause 时若未正确停 AudioWorklet（或停太慢），AudioContext 可能继续读 video → 触发 video 内部状态变化 → 导致 UI 跳变。

### 最佳方案

1. **改用响应式 ref 管 `suppressPauseEvent`**（或用 debounce 防抖 handlePause）。
2. **排查后端 pause/resume 是否回发事件**：grep `backend/app/api/ws.py` 确认 `pause_session` / `resume_session` 的处理；若回发则去掉或前端忽略。
3. **pause 时先停 AudioWorklet**：在 `pauseMedia` 调 `session.pauseCapture()` → 停采集 → 再 `element.pause()`；play 时反之。
4. **测试**：多次点击 pause/play，观察按钮状态与视频播放是否一致。

## 问题 3/4：桌面投送与报告流程不明确（🟡 UX/文档）

### 用户疑问
> 3. 投送桌面悬浮框的功能是怎么实现的？实现了吗？
> 4. 桌面悬浮框结束之后我们应该走什么流程？是否有报告生成的功能？

### 实际实现（已读 `session.ts openDesktopFloating` + `desktop App.vue`）

**投送流程（已实现）：**
1. Web 端 `openDesktopFloating()` → 调后端 `issueSessionHandoff` 签发一次性 token（300s TTL）。
2. 拼 deep-link `lingosync://floating/start?sessionId=...&token=...`。
3. 浏览器唤起桌面 App（Tauri single-instance 转发给运行中进程）。
4. 桌面 `claimHandoffToken` 兑 `ws_token` → 连 WS → 后端 `session_event_hub` 重放历史 + 转发实时。
5. 桌面 App 显示单句悬浮字幕（`FloatingCaption`）。

**报告流程（已实现）：**
- **Web 端**：结束 → WS 收 `session_report` 事件 → `state="report"` → UI 显示报告卡片 + 下载按钮（TXT/SRT/MD/JSON）。
- **桌面端**（`App.vue:318-370`）：
  - standalone 模式结束 → 调 `waitForReport()` 轮询 + WS `session_report` 事件双路径 → 拿到 `reportId`。
  - 自动触发下载（`triggerReportDownload`）→ 用户选路径。
  - handoff 模式**无报告**（只显示实时字幕，结束即关窗）。

### 问题根因
**功能已实现，但用户不知道怎么用 = UX/文档问题**。

### 最佳方案
1. **补 README / 用户指南**：明确投送按钮位置、报告下载流程、桌面端两种模式差异（standalone 有报告、handoff 无报告）。
2. **桌面端 handoff 模式增提示**："本次会话由 Web 端发起，报告请在 Web 端下载"。
3. **Web 端"激活桌面"按钮旁补 tooltip**："投送到桌面悬浮窗，Web 端继续显示完整字幕"。

## 批次2实际落地记录

### DashScope LiveTranslate VAD 调研结论

2026-06-16 复查阿里云百炼官方 LiveTranslate 实时 API 文档：

- `session.update` 文档公开字段包括 `modalities`、`voice`、`input_audio_format`、`output_audio_format`、`input_audio_transcription.model/language`、`translation.language/corpus` 等。
- 官方事件流包含 `input_audio_buffer.speech_started` / `input_audio_buffer.speech_stopped` / transcription completed / response text done，说明起止检测由服务端自动产生。
- 未查到 `vad_threshold`、`silence_duration`、`split_on_punctuation`、`turn_detection` 等可配置参数。

因此本批未向 `backend/app/services/providers/dashscope/realtime.py` 增加非公开 VAD 字段，避免向云端发送未确认配置导致兼容风险；实际采用管线侧二次切分与去重。

### 实际采用方案

- `backend/app/services/pipeline.py`：
  - 将 LiveTranslate 单 turn 的源文/译文先按句号、问号、感叹号和长度切为可读展示块，再按相对顺序对齐，不再要求源文句数与译文句数完全相等。
  - 英文按句子、逗号/分号/冒号和最大词数拆分；中文按句子和长译文字符阈值拆分，避免 20s 以上长字幕挤在一个卡片里。
  - 对 CJK 短语级重复做塌缩，覆盖“从最黑暗的深处走来，从最黑暗的深处走来”这类相邻短语重复。
  - 保留已拆分 partial 的既有子段，避免后续 partial 变短时 UI 折回单段。

- `frontend/src/components/workbench/MediaPanel.vue`：
  - 程序性暂停统一 silent，不再把 watcher 触发的 `element.pause()` 反灌为用户暂停事件。
  - `pause` / `play` 原生事件加短窗口防抖，减少浏览器控件和会话状态互相触发造成的快速跳变。

- 清理与说明：
  - 删除 `/sessions/{id}/media` 上传路径和 `upload_video` / `upload_audio` 输入模式残留，文档改为“本地视频/音频（浏览器播放采集）”。
  - `/api/models/strategy/plan` 增加 disclaimer，明确 gummy/fun_asr 仍是策略蓝图，未接入真实管线。
  - 桌面 handoff 模式增加“本次会话由 Web 端发起，报告请在 Web 端下载”提示。
