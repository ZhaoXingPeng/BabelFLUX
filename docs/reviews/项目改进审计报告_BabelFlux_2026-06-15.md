### 1.2 行业架构共识（对我们极其有利）

> 调研一致指出：**90% 的生产级同传部署都用"三段级联"架构——语音转文本 → 文本翻译 → 译文转语音**（Interprefy / KUDO / Wordly / 各大厂底层皆然）。级联设计的好处是：**每一段可独立调试、可热插拔、各自有成熟合规故事。**

这一行业事实**直接背书了 BabelFlux 的分层链路**（LiveTranslate 实时识别+翻译 → qwen-flash 实时纠偏 → qwen-plus 会后全局校正），并为"为何不做端到端"提供了标准答案（见汇报报告 Q&A）。

### 1.3 市场空白 = BabelFlux 的差异化定位

调研所有竞品后，三个**几乎无人正面产品化**的空白，正是 BabelFlux 的护城河：

1. **"输出后还能回头改对"（retroactive / 在线纠偏）**——竞品都在拼"延迟"和"边听边说"，讯飞提"消除割裂感"，但**"传译进行中、随后文到达自动修正已经输出的前句术语/数字/否定/一词多义错误"几乎是 BabelFlux 独有的产品化卖点**。这是最大的差异化亮点。
2. **个人 / 零部署 / 任意音源 / 桌面全局悬浮**——竞品多为会议 SaaS、活动平台或硬件（如时空壶）。BabelFlux 面向**个人看网课、看 YouTube/B 站、线下听讲座**这种长尾场景：浏览器标签页/系统音频/屏幕/麦克风任意接入，桌面透明悬浮窗全局置顶，不绑定任何会议平台。
3. **可降级 / 零配额演示**——`MODEL_PROVIDER=mock` 即可零成本跑通全链路，竞品 demo 普遍依赖在线服务与配额。工程务实性，利于评审与试用。

> ⚠️ 竞品多为**大模型自研 + 海量数据**的重资产玩法（讯飞、字节）。BabelFlux 是**编排型应用**（站在 DashScope 之上做产品化与体验），汇报时应主动把战场拉到**"产品形态 + 体验工程 + 纠错机制"**，而非和大厂比延迟数字和语种数量。

## 2. 本项目问题与可优化点（按重要性排序）

> 每条标注：严重度（🔴高 / 🟠中 / 🟡低）、证据 `file:line`、影响、建议方向（**仅方向，本审计不改代码**）。
> 标 ⭐ 的 **Top 3** 将作为《项目汇报审计报告》三大技术解构的"诚实工程"环节。

### ⭐ #1 🔴 主 WebSocket 路径无鉴权（生产化最大缺口）
- **证据**：`backend/app/api/ws.py:58` 主路径 `session_store.get_or_create(session_id)` 直接放行；只有 handoff 路径 `ws.py:49` 才校验 token。
- **影响**：任何知道/猜到 `session_id`（UUID）的人都能连上、注入 `start_session` 驱动**真实模型计费**、并接收他人转写内容。叠加"真实链路无成本护栏"，可被刷量。
- **建议方向**：主路径也要求一次性票据/登录态；或在 demo 环境显式声明"无鉴权仅限本机演示"。**这恰恰反衬 handoff 路径的 token 设计很专业**——可作为汇报里"我们知道差距在哪"的诚实点。

### ⭐ #2 🟠 "客户端时钟双向同步"名实不符（实为单向只读观测）
- **证据**：`pipeline.py:231` `update_client_clock` 只存 `_client_playback_ms`；权威时钟 `elapsed_ms` 由**喂入字节累加**得到（`pipeline.py:210` / `:243`）；客户端时钟仅在 `_emit_client_clock_sync_if_due`（`pipeline.py:1074`）里算出 `lag_ms` **发一条状态消息**，**从不回写**段落时间码。叠加 `ws.py:330` 队列满丢最旧帧的策略，丢帧后 `elapsed_ms` 与真实播放钟漂移→字幕时间码偏移。
- **影响**：README/架构文档称"客户端时钟双向同步"属**过度声明**；长时间丢帧下时间码与画面会越来越不准。
- **建议方向**：要么把 `playback_ms` 真正用于校正段落时间码（变成真双向），要么把文案改为"客户端时钟观测/对齐提示"。

### ⭐ #3 🟠 实时纠偏并发重入无幂等保护
- **证据**：`pipeline.py:969` `_on_segment_complete` 对**每句完成**都 `create_task` 复核最近窗口；`_apply_revision`（`pipeline.py:986`）**不校验 `seg.status=="revised"`**。窗口（`revision.py` window=4）重叠时，同一句可被两个复核任务先后改写，`revision.py:156` 的 `before` 取到的是**当前译文**（可能已被前一任务改过）→ 振荡/重复修正记录。
- **影响**：偶发"改了又改"、修正记录重复、置信度不一致。`revision.py:92` 的 6 次/分钟限速只约束 LLM 调用频次，不约束对同一句的重入。
- **建议方向**：对"已 revised 的句子"加幂等/版本号校验；或对同一 segment 串行化复核。

### #4 🟠 TTS 接收侧未实现——"语音呈现"在端到端链路上不成立
- **证据**：`realtime.py:168` 会发 `kind=="audio"` 事件、`realtime.py:191` 在 `tts_enabled` 时配置 `modalities:["text","audio"]`；但 `pipeline.py:275` 的 `_handle` **没有处理 `audio` 分支**；前端全局 grep `ttsEnabled` 无任何置 `true` 处。
- **影响**：README"双语字幕 **/ 语音** 呈现"的"语音"目前**无端到端支撑**。因默认关闭，当前无计费、无坏功能，但**汇报不可宣称 TTS 可用**。
- **建议方向**：要么补 `_handle` 的音频接收+下发+前端播放，要么把"语音合成"标注为"规划中/可选"。

### #5 🟠 上传文件→后端 ffmpeg 解码为死代码 + README 过度声明
- **证据**：`session.ts:150` 的 `inputModeBySourceKey` 把 `video-file`/`audio-file` 映射到 **`media_element_audio`**（前端用 AudioWorklet 从播放中的 `<video>` 采集），**永不产生 `upload_video`/`upload_audio`**；于是 `session.ts:1236` 的上传分支、`uploadSessionMedia`、后端 `sessions.py:124` 上传端点 + `ws.py:253` 的 ffmpeg 解码路径**全部不可达**。
- **影响**：README 输入源表里 `upload_video / upload_audio → ffmpeg 解码上传文件`描述的链路实际走不到；两套并行实现，后端一套是死代码，增加维护与理解成本。
- **建议方向**：删除未用的后端上传链路（或在前端补一个真正走它的入口）；README 据实改为"上传文件经客户端媒体元素采集"。**注：前端选 `media_element_audio` 而非后端 ffmpeg，是为了"画面与模型输入同源、避免双时钟"——这其实是优点（见汇报报告主题二），但死代码与文档要清理。**

### #6 🟠 会话 / handoff / 事件全部进程内内存，无持久化与水平扩展
- **证据**：`session_store.py:84`、`handoff.py:40`、`session_events.py:17` 均为内存单例（`session_store.py:6` 注释自认"如需多进程/持久化可换 Redis/SQLite"）；`session_events.py:18` replay 历史上限 100 条。
- **影响**：进程重启丢失运行中会话与 handoff token（报告已落盘可容错）；无法多 worker / 多机部署；handoff 接管时若历史超 100 条会丢早期字幕。
- **建议方向**：生产化用 Redis/DB 承载会话与事件；明确单机演示边界。

### #7 🟡 长会话前端 O(n²) 且无字幕虚拟滚动
- **证据**：`session.ts:707` `transcriptPairs` getter 每个字幕事件全量重建；`session.ts:443` `combinedTimeline` 在 `.map` 内嵌套 `.find`（O(n²)）；DOM 渲染全部句对。
- **影响**：数百句以上的长演讲，每个 partial 事件都触发全量重算 + 全量渲染，性能与内存随时长劣化。
- **建议方向**：增量维护配对索引（Map）、列表虚拟滚动。

### #8 🟡 无 WebSocket 断线重连
- **证据**：`session.ts:1525` `connectSocket` 的 `onClose` 仅置状态，无重连/退避。
- **影响**：网络瞬断即结束会话（后端内存态本身也难续，与 #6 相关）。
- **建议方向**：客户端指数退避重连 + 服务端会话续接（依赖 #6 持久化）。

### #9 🟡 多目标语种 / `modelProfile` / 源语种 auto 多为"装饰性 UI"
- **证据**：`session.ts:109` `targetLanguageOptions` 含英/日/韩，但后端 LiveTranslate 与纠偏/报告 prompt 偏向中文输出；`sessions.py:96` 源语种 `auto`→强制 `en`；`session.ts:1199` 发送的 `modelProfile`（快速低延迟/高准确/成本优先…）在 `sessions.py:99` `_register_session` **未透传**、`SessionRecord` 也**无该字段**→后端丢弃。
- **影响**：UI 暴露的能力与后端实际能力不符，被追问会露怯。
- **建议方向**：要么把这些选项真正接进后端（语种/模型档位驱动选型），要么收窄 UI 到已支撑的范围。

### #10 🟡 声明 sqlmodel 依赖却零使用 + 大量静默吞异常
- **证据**：`backend/pyproject.toml:14` 声明 `sqlmodel`，全项目无 `SQLModel/create_engine/Session` 使用（`config.py:21` `database_url` 仅是配置字符串）；`pipeline.py:981` `_run_review`、`ws.py:369` `_build_llm_client` 等多处 `except Exception` 静默吞。
- **影响**：冗余依赖 = 技术栈过度声明；静默吞异常使生产期纠偏/链路失败难观测。
- **建议方向**：移除未用依赖或落地一个最小持久化；关键异常至少打日志/计数。

> 其余轻微项（备查，不计入 Top 10）：`localStorage` 键名仍为 `lingosync.clientSeen`（`session.ts:944`，品牌遗留）；模块级可变单例（`session.ts:44-60` 的 `socket`/`estimatedOutputLatencyMs` 等）在多实例/SSR 下共享全局；`fixture` 演示路径与真实路径在 store 内有两套并行逻辑（维护成本，但保障了零后端可演示）。

## 4. 改进路线图（按"演示安全 vs 生产化"分层）

**面试前必做（低成本、防露怯）：**
1. 文档据实校正：README 的"双向同步""语音呈现""上传 ffmpeg 解码""多语种"四处措辞改为与代码一致（对应 #2/#4/#5/#9）。

**短期（1–2 天工程量）：**
3. 纠偏幂等保护（#3）；移除上传死代码 + sqlmodel 冗余依赖（#5/#10）。
4. 主 WS 路径加最简票据校验或环境开关（#1）。

**中期（生产化）：**
5. Redis/DB 承载会话+事件+handoff（#6）→ 解锁断线重连（#8）与多机部署。
6. 客户端时钟真正回写时间码（#2 升级为真双向）。
7. 前端配对索引 + 虚拟滚动（#7）。

**长期（产品化）：**
8. 落地 TTS 接收侧 + 多目标语种 + modelProfile 真正驱动选型（#4/#9），把"装饰"变"能力"。
