开发与提交规范
版本：v0.1

一、开发节奏
1. 保持持续提交，不在最后一天一次性导入全部代码。
2. 每个功能使用独立分支开发，通过 PR 合并。
3. 主分支 main 合并后应保持可运行或可审阅状态。
4. 大功能拆成多个小 PR，降低评审和回滚成本。

二、分支命名建议
1. feat/功能名：新增功能。
2. fix/问题名：修复缺陷。
3. docs/文档名：文档调整。
4. chore/任务名：工程配置、依赖、初始化等非业务改动。

三、提交信息建议
1. feat: 新增某功能
2. fix: 修复某问题
3. docs: 补充某文档
4. chore: 完成某工程任务

四、PR 标题建议
格式：类型: 一句话说明新增或修改内容

示例：
1. feat: 新增场景选择入口
2. docs: 补充小说转剧本 YAML Schema
3. fix: 修复实时字幕修正状态更新

五、PR 描述必须包含
1. 功能描述：说明该功能的作用与使用方式。
2. 实现思路：说明技术选型或核心实现逻辑。
3. 测试方式：说明如何验证功能正常运行。

六、注意事项
1. PR 描述不能空白，也不能与实际变更严重不符。
2. 第三方库或框架需要在 README 中列明。
3. 如果复用过去的代码片段，需要在 PR 描述中注明来源。
4. 提交时间应保持在项目有效开发周期内。
