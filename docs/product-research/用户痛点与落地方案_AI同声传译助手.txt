AI 同声传译助手 - 用户痛点调查与落地方案
版本：v0.1
日期：2026-06-05

一、调研目标
本阶段目标是从用户痛点出发，确认 AI 同声传译助手的真实价值点，并将痛点转化为可开发、可演示、可通过 PR 持续交付的具体方案。

最终选题：
选题二：AI 同声传译助手

产品一句话定位：
面向国内用户观看外语视频、网课、技术分享和跨国会议的实时字幕同传助手，优先解决“源语言字幕不同步、字幕不显示、翻译延迟、术语错、翻译字幕无法修正、记录难复用”的问题。

二、目标用户
1. 技术学习者
经常观看英文技术分享、开源社区会议、国外网课、产品发布会，需要快速理解内容。

2. 职场用户
参加跨国会议、远程培训、英文 Webinar，希望降低听力门槛并保留会议记录。

3. 学生与研究者
观看英文课程、学术讲座或国际会议视频，需要双语对照、术语一致和可导出笔记。

4. 内容运营与知识整理者
需要把外语音视频整理成中文摘要、字幕和双语资料，提高内容再利用效率。

三、国内相关产品与使用场景观察
本项目需要优先观察国内用户的真实使用环境。国内用户经常在百度网盘、B 站、腾讯会议、钉钉会议、浏览器网课、YouTube、Coursera、国外技术大会回放等场景中接触外语内容。很多平台已经提供“字幕”或“字幕翻译”，但体验并不稳定。

关键观察：
1. 百度网盘、在线视频平台和部分浏览器字幕插件可以提供字幕或字幕翻译，但用户常遇到字幕不同步、字幕不显示、需要手动开启、页面兼容失败、视频源不支持等问题。
2. 如果源语言字幕本身都不能稳定同步，那么后续实时翻译和准确翻译无从谈起。因此本项目第一层问题不是“翻译得多准”，而是“能否稳定拿到与音频同步的源语言文本”。
3. 腾讯会议等会议产品已经支持实时字幕、翻译字幕和双语字幕显示，但能力仍然在平台内部，用户无法把同一套体验自然迁移到百度网盘、浏览器网课或任意网页视频。
4. 讯飞同传等成熟产品已经以实时字幕、翻译字幕、浏览器插件或悬浮窗形式存在，证明“悬浮字幕同传”是用户可以理解的产品形态。
5. YouTube 等国外平台也提供自动字幕和翻译字幕，但实际使用中仍可能出现字幕缺失、同步延迟、翻译不自然、术语错误等问题。

调研来源：
1. 腾讯会议实时字幕和翻译字幕支持文档：https://meeting.tencent.com/support-doc-detail/1174/index.html
2. 讯飞同传官网：https://tongchuan.iflyrec.com/
3. Google Meet translated captions: https://support.google.com/meet/answer/10964115
4. YouTube automatic captions: https://support.google.com/youtube/answer/6373554

四、产品定义修正
本项目中的“同声传译”不等于首版必须同步播放中文语音。

更准确的定义：
1. 广义同声传译
源语言正在播放时，系统尽量同步地将内容转换为用户能理解的语言。输出形式可以是字幕，也可以是语音。

2. 本项目 MVP 定义
本项目首版聚焦“实时字幕同传”。用户继续听原始音频，系统以悬浮字幕或页面字幕形式同步展示源语言文本和中文翻译。

3. 不优先做中文语音播报
中文语音播报会引入更高延迟，也可能遮挡原始音频。对于技术分享、网课和会议旁听场景，字幕比语音更适合作为 MVP。

4. 后续可扩展中文语音
当字幕链路稳定后，可以增加中文 TTS、原音压低、分句播报等能力，但这应作为第二阶段功能。

5. 产品形态
理想形态接近“浏览器插件或悬浮窗字幕助手”：不强依赖某一个平台，在用户观看网页视频、会议或本地音频时提供同步源语言字幕和中文字幕。

五、核心用户痛点
1. 源语言字幕同步不稳定
这是第一优先级痛点。用户在百度网盘、网页视频或 YouTube 等场景中，经常遇到字幕不显示、字幕加载失败、字幕延迟或字幕与音频错位。若源语言文本无法稳定同步，后续实时翻译和准确翻译都无法成立。

2. 平台绑定严重
用户并不只在一个平台上听外语内容。会议软件、浏览器视频、网课平台、本地音频文件、直播回放都可能需要翻译。如果能力只存在于某个平台内，用户跨平台使用成本很高。

3. 听不懂时无法及时补救
外语演讲语速快、信息密度高。用户一旦漏听关键句，后续内容也容易跟不上。传统字幕只显示当前内容，不能很好地帮助用户回看、定位和修正理解断点。

4. 技术术语翻译不稳定
技术分享中有大量框架名、API、模型名、缩写、论文术语和公司产品名。通用翻译经常出现同一个术语前后翻译不一致，或把专有名词误翻成普通词。

5. 字幕错误没有明确修正机制
实时识别和翻译常会先输出临时结果，后续上下文明确后才知道前面错了。如果产品不支持历史字幕修正，用户会被早期错误持续误导。

6. 低置信度内容不可见
用户不知道哪一句字幕是系统非常确定的，哪一句是可能有误的。没有置信度或修正提示，用户难以判断哪些内容需要回看。

7. 缺少双语记录和复用能力
很多用户不只是想“当场听懂”，还想保留双语对照、关键术语和会议摘要。如果只显示即时字幕，内容结束后价值就消失了。

8. 语音播报并非首要需求
中文语音同传有价值，但会增加延迟和打断感。对于技术分享、网课和会议旁听，用户通常更需要低延迟、稳定、可回看的中文字幕。

9. 噪声、口音和多人说话影响大
真实场景中存在口音、语速快、麦克风质量差、背景噪声、多人重叠说话等问题。产品需要给出降级策略，而不是假设输入永远干净。

六、痛点到功能映射
1. 源语言字幕同步不稳定
落地功能：建立“源语言同步状态”机制，至少展示 listening、syncing、lagging、missing、recovered 状态；当源文本缺失或延迟时提示用户，而不是静默失败。

2. 平台绑定严重
落地功能：支持麦克风输入、浏览器标签页音频、上传音频或演示音频。MVP 可先支持麦克风输入和预置演示音频。

3. 听不懂时无法补救
落地功能：实时字幕流、历史字幕列表、当前句高亮、双语对照回看。

4. 术语翻译不稳定
落地功能：会话级术语表，支持 source_term、target_term、domain、priority、note。

5. 字幕错误不能修正
落地功能：字幕片段使用 segment_id、version、status 管理，支持 partial、final、revised 状态。

6. 低置信度不可见
落地功能：为识别结果和翻译结果保留 confidence 字段，低置信度字幕用样式标记。

7. 内容不能复用
落地功能：导出双语记录，后续扩展为字幕文件、会议摘要和术语清单。

8. 语音播报影响低延迟
落地策略：MVP 聚焦字幕同传，中文语音播报放到后续版本。

9. 输入质量不稳定
落地策略：MVP 提供 mock/演示模式，保证评审 Demo 稳定；真实音频输入作为增强能力。

七、MVP 范围
MVP 名称：
跨平台实时字幕同传助手

MVP 不追求完整会议插件，也不优先做中文语音播报，而是先完成一个可演示的 Web 应用或悬浮字幕页面，验证源语言同步、字幕翻译、字幕修正和双语记录闭环。

必须包含：
1. 创建同传会话。
2. 选择源语言和目标语言。
3. 输入音频或使用预置演示音频。
4. 展示源语言同步状态。
5. 实时展示源语言文本。
6. 实时展示中文字幕。
7. 支持字幕状态：partial、final、revised。
8. 支持历史字幕修正。
9. 支持基础术语表。
10. 支持双语记录导出。

暂不包含：
1. 中文语音播报。
2. 多会议平台插件。
3. 多人说话人分离。
4. 高级降噪。
5. 完整多语种矩阵。

八、工具选型与实现优先级
本项目需要避免重复造轮子。除核心业务逻辑外，音视频处理、悬浮窗口、字幕格式、模型调用和语音播报都应优先使用成熟工具。

1. 输入方式优先级
P0：演示视频/演示音频
用于稳定展示完整闭环，避免真实网页音频权限、网络和跨域问题影响评审。

P0：上传视频
用户可以上传本地视频。系统从视频中提取音频做 ASR，同时在网页中播放原视频，并叠加字幕。相比只上传音频，上传视频更贴近用户真实需求，优先级应更高。

P1：浏览器标签页/屏幕音频捕捉
用户可以播放百度网盘、YouTube、网课或会议页面，然后授权浏览器捕捉标签页或屏幕音频。该能力最接近最终产品，但受浏览器权限、系统音频支持和用户授权影响。

P1：上传音频
适合会议录音、播客、课程音频和快速测试。实现简单，但用户体验不如上传视频直观。

P2：视频链接
用户可以输入视频链接，但只优先支持公开视频直链或可直接访问的 MP4/音频链接。百度网盘、B 站、YouTube 等平台链接通常涉及登录、跨域、反爬、加密或版权限制，不应作为 MVP 主链路。对于这类页面，推荐通过“浏览器音频捕捉”实现。

P2：麦克风
适合线下外放、会议室或旁听场景，但对网页视频不稳定，容易录到环境噪声。因此麦克风不是观看视频同传的首选输入。

2. 字幕输出优先级
字幕输出是最高优先级能力。

必须实现：
1. 源语言字幕。
2. 中文字幕。
3. 源语言同步状态。
4. 实时纠偏展示。
5. 历史双语记录。

字幕形态：
1. 视频底部字幕：适合上传视频和演示视频。
2. 可拖动悬浮字幕窗：适合模拟插件体验。
3. 右侧双语记录面板：适合回看和导出。
4. 最终报告页：适合展示最终纠偏。

可直接使用的工具：
1. vue3-draggable-resizable：用于实现可拖动、可缩放悬浮字幕窗。
2. Floating UI Vue：用于处理悬浮元素定位、避让和可访问性交互。
3. Video.js：用于网页视频播放和字幕轨道能力。
4. subtitle 或 webvtt-parser：用于解析、生成 SRT/WebVTT 字幕。

3. 语音输出策略
语音同步实现，但由用户选择是否开启。

MVP 策略：
1. 字幕不等语音，字幕先出。
2. 中文语音只在用户开启后播放。
3. 语音播报基于 final 或 revised 后的中文句子，避免临时翻译反复播报。
4. 如果原视频由我们控制，可以提供“降低原音音量”选项。
5. 如果原视频来自外部网页，只播放中文 TTS，不强行控制原网页音量。

可直接使用的工具：
1. Web Speech API SpeechSynthesis：浏览器内置 TTS，适合 MVP 快速验证。
2. edge-tts：Python 侧可调用的在线 TTS 工具，适合生成中文语音。
3. CosyVoice：更适合后续做高质量中文 TTS 或流式 TTS。

4. 音视频处理工具
1. ffmpeg.wasm：可在浏览器中处理音视频，适合轻量提取音频，但大文件性能可能受限。
2. FFmpeg 服务端：适合稳定处理上传视频，提取音频、切片和转码。
3. MediaRecorder：适合录制浏览器捕捉到的音频流。
4. getDisplayMedia：适合捕捉屏幕、窗口或标签页音视频流。

5. 语音识别模型
MVP 建议优先选择“可快速接入 + 支持时间戳 + 可离线或自托管”的方案。

候选：
1. FunASR：国内生态更友好，支持流式和离线 ASR，并包含 VAD 分割能力，适合中文团队快速接入。
2. SenseVoice：适合多语种语音理解，覆盖普通话、英语、粤语、日语、韩语等场景，可作为后续增强方案。
3. faster-whisper：Whisper 的高性能实现，适合上传音视频后的离线转写和字幕生成。
4. sherpa-onnx：适合后续考虑端侧或本地部署。

MVP 推荐：
1. 上传视频/演示音频：优先 faster-whisper 或 FunASR 离线处理。
2. 实时流式字幕：优先 FunASR 流式能力，或先用 mock 流式数据验证产品闭环。
3. 演示兜底：必须保留 mock 字幕流，保证评审稳定。

6. 翻译与大模型纠偏
实时翻译和最终纠偏可以都接入大模型，但策略不同。

实时阶段：
1. 以低延迟为主。
2. 只对最近几句做轻量纠偏。
3. 优先使用术语表、规则和上下文窗口。
4. 大模型只参与高风险片段，例如术语、否定、数字、人名、关键结论。

最终阶段：
1. 建议接入大模型纠偏。
2. 使用完整源语言转写、中文字幕、术语表、RevisionEvent 和同步日志。
3. 输出最终双语稿、修正记录、术语总结和会话摘要。
4. 要求大模型输出结构化 JSON，避免只生成不可校验的自然语言。

模型调用框架：
1. 自研 Python Provider Gateway：基于统一接口适配不同 ASR、LLM、TTS 供应商。
2. LiteLLM：作为 Python 后端多模型 Provider 抽象的可选工具。
3. 不建议早期引入过重 Agent 框架，当前任务是稳定字幕和纠偏，不是复杂 Agent。

7. 页面设计方向
页面需要看起来像一个可信的实时工具，而不是普通表单页面。

视觉方向：
1. 主色：墨蓝、海盐白、青绿色状态光，不使用默认紫色风格。
2. 状态色：syncing 用青绿，lagging 用琥珀，missing 用红橙，revised 用蓝色。
3. 字体：中文使用 Noto Sans SC 或 HarmonyOS Sans，英文标题可用 Space Grotesk。
4. 背景：轻微网格、玻璃拟态字幕窗、低干扰渐变。

核心界面：
1. 顶部：会话状态、输入来源、语言方向、TTS 开关。
2. 中心：视频播放区或演示区。
3. 底部：大字号双语字幕。
4. 右侧：实时双语记录、修正记录、术语命中。
5. 悬浮窗：可拖动、可缩放、可折叠。
6. 结束页：最终纠偏报告和导出入口。

九、产品核心流程
1. 用户进入首页，点击“开始同传”。
2. 用户选择输入方式：演示视频/音频、上传视频、浏览器音频捕捉、上传音频、视频链接、麦克风。
3. 用户选择语言：源语言英语，目标语言中文。
4. 用户可选上传或编辑术语表。
5. 系统开始会话，先展示源语言同步状态。
6. 系统展示源语言字幕和中文字幕。
7. 系统先输出临时字幕，随后基于上下文更新为最终字幕。
8. 如果源字幕缺失或延迟，系统提示 lagging 或 missing，而不是让用户误以为没有内容。
9. 如果后续识别或翻译发现错误，系统更新历史字幕，并记录修正原因。
10. 会话结束后，用户查看双语记录、术语命中和修正记录。
11. 用户导出双语文本或演示报告。

十、系统模块设计
1. 前端展示模块
负责会话创建、音频输入、字幕展示、历史记录、术语表编辑和导出入口。

2. 音频输入模块
MVP 支持预置演示音频和麦克风输入。浏览器标签页音频或系统音频作为后续扩展。

3. 源语言同步状态模块
负责判断当前是否正常收到源语言文本，并输出 listening、syncing、lagging、missing、recovered 等状态。该模块是翻译前置条件。

4. 流式识别模块
将音频切分为片段，输出 source_text、start_time、end_time、confidence、status。

5. 翻译模块
基于源语言文本、上下文窗口和术语表生成中文字幕。

6. 修正模块
维护最近若干条字幕的可修正窗口，生成 RevisionEvent，并让前端按 segment_id 更新历史字幕。

7. 术语表模块
管理术语、目标译名、领域、优先级和备注，翻译时优先使用术语表。

8. 记录导出模块
导出双语记录、修正记录和术语命中结果。MVP 可先导出 TXT 或 JSON。

十一、核心数据对象
1. Session
字段包括 session_id、source_language、target_language、input_mode、status、source_sync_state、started_at、ended_at。

2. TranscriptSegment
字段包括 segment_id、session_id、source_text、start_time、end_time、confidence、status、version。

3. TranslationSegment
字段包括 segment_id、session_id、target_text、display_text、status、version、glossary_hits、revised_from。

4. RevisionEvent
字段包括 revision_id、segment_id、type、old_text、new_text、reason、severity、confidence、visible、created_at。

5. GlossaryItem
字段包括 glossary_id、source_term、target_term、domain、priority、note。

6. SessionReport
字段包括 report_id、session_id、summary、final_transcript、final_translation、revision_events、glossary_summary、sync_summary、export_urls。

十二、字幕状态设计
1. partial
系统基于实时识别先输出的临时字幕，低延迟但可能变化。

2. final
当前片段识别和翻译已稳定，作为正式字幕展示。

3. revised
后续上下文发现前文有错误，系统对历史字幕进行了修正。

十三、实时纠偏与最终纠偏设计
本项目需要同时展示两类纠偏：
1. 实时纠偏：看视频或听会议时直接展示在字幕行上。
2. 最终纠偏：会话结束后以最终报告形式展示。

这两类纠偏不是同一件事。实时纠偏强调低延迟和可感知；最终纠偏强调完整上下文和更高准确度。

1. 实时纠偏
实时纠偏只处理最近几条字幕，建议窗口为最近 3 至 5 条，或最近 20 至 40 秒。

实时纠偏触发条件：
1. ASR 临时识别结果变为最终识别结果，源语言文本发生明显变化。
2. 后续上下文补足，发现前一句翻译意思不完整或不准确。
3. 术语表命中，发现某个术语需要统一翻译。
4. 识别到数字、日期、否定词、人名、产品名等高风险信息变化。
5. 源语言同步状态从 lagging 或 missing 恢复，需要补齐或修正历史字幕。

实时纠偏展示方式：
1. 被修正字幕行显示 revised 状态。
2. 修正瞬间轻微高亮，不大面积闪烁。
3. 显示简短原因，例如“术语修正”“上下文修正”“源文本修正”。
4. 用户可以展开查看 old_text 和 new_text。
5. 轻微表达优化不实时修，避免干扰观看。

实时纠偏示例：
原字幕：
这个模型延迟很敏感。

实时修正后：
这个模型对延迟很敏感。

修正原因：
表达修正，使中文更自然。

2. 最终纠偏
最终纠偏在会话结束后执行，使用完整上下文、完整术语表和全部 RevisionEvent 生成最终报告。

最终纠偏处理内容：
1. 全量源语言转写。
2. 全量中文翻译。
3. 实时纠偏记录。
4. 未实时展示的低优先级修正。
5. 术语一致性修正。
6. 字幕同步问题统计。
7. 最终双语记录导出。

最终报告结构：
1. 会话摘要。
2. 最终双语转写。
3. 实时纠偏记录。
4. 最终纠偏记录。
5. 术语命中与术语修正。
6. 源语言同步质量统计。
7. 导出入口。

最终报告示例：
时间：00:01:12 - 00:01:16
类型：术语修正
原翻译：检查点
最终翻译：模型检查点
原因：checkpoint 在机器学习语境中应译为模型检查点。

3. MVP 实现策略
MVP 可以先用 mock 字幕流稳定展示纠偏闭环：
1. 模拟输出一条临时源语言字幕。
2. 模拟输出一条临时中文翻译。
3. 两秒后触发 RevisionEvent。
4. 前端将对应 segment 标记为 revised。
5. 会话结束后生成 SessionReport。

真实能力接入后，RevisionEvent 可由 ASR final、上下文翻译、术语表命中和源语言同步状态共同触发。

十四、关键体验指标
1. 源语言同步可用性
目标：系统能明确判断当前是 syncing、lagging 还是 missing，不出现无提示的静默失败。

2. 首屏字幕出现时间
目标：开始播放后 1 至 2 秒内出现第一条字幕。

3. 单句最终稳定时间
目标：一句话结束后 2 至 5 秒内转为 final。

4. 修正可理解性
目标：修正不要频繁闪烁；只修正影响理解的错误。

5. 术语一致性
目标：术语表命中的词前后翻译一致。

6. 演示稳定性
目标：即使真实音频能力不稳定，也能通过预置演示数据完整展示产品闭环。

十五、Demo 方案
为了保证评审稳定，Demo 优先使用国内用户熟悉的观看场景进行抽象演示，例如“浏览器网页视频/网盘视频/YouTube 技术视频”的悬浮字幕同传。技术实现上可先使用预置英文技术分享音频或模拟流式数据。

演示脚本：
1. 打开应用首页。
2. 展示悬浮字幕面板或同传面板。
3. 创建同传会话。
4. 选择英语到中文。
5. 导入术语表，例如 Transformer、latency、streaming、checkpoint。
6. 开始播放演示音频。
7. 展示源语言同步状态从 listening 到 syncing。
8. 展示实时源语言字幕和中文字幕。
9. 模拟一次源字幕 lagging 或 missing，并展示恢复提示。
10. 故意让某一句先出现不准确翻译，随后通过 revised 状态修正。
11. 展示术语命中。
12. 结束会话，展示最终纠偏报告。
13. 导出双语记录。

十七、主要风险与降级方案
1. 真实 ASR 接入不稳定
降级：先用 mock 流式字幕和预置音频保证 Demo。

2. 浏览器系统音频采集受限制
降级：MVP 支持上传音频和预置演示音频，系统音频作为后续扩展。

3. 修正过于频繁影响阅读
降级：只修正最近 N 条且影响理解的字幕；低价值修正只记录到会话报告。

4. 翻译术语不一致
降级：优先使用术语表；无术语时保留英文原词加中文解释。

5. 延迟过高
降级：字幕优先，不做语音播报；使用短片段和临时字幕。

十八、阶段结论
本项目不应只做“实时翻译字幕”，否则容易与平台自带能力或讯飞同传等成熟产品同质化。核心落地点应是：
1. 先保证源语言字幕同步可感知、可恢复、可解释。
2. 提供跨平台或弱平台绑定的悬浮字幕同传体验。
3. 面向技术内容提供术语一致性。
4. 支持可修正的历史字幕。
5. 明确展示实时纠偏。
6. 通过最终报告展示最终纠偏。
7. 支持可导出的双语记录。
8. 形成稳定可演示的字幕同传闭环。

下一步应进入工程实现阶段，优先做上传视频/演示视频、字幕输出组件、源语言同步状态、mock 流式字幕和字幕修正机制，确保最早形成可展示的产品闭环。
