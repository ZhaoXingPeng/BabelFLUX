# 上传视频实时同步优化修正方案

## 目标

面向“上传视频在线同传实验”，优先优化输出同步率，让视频画面、音频、源文、译文和右侧字幕视野尽可能一致。

核心目标：

- 上传视频播放后，后端收到的音频流与前端视频播放进度使用同一个时间源。
- 右侧字幕始终跟随当前输出字幕，并把当前字幕保持在视野中心。
- 源文和译文严格按同一个 segment 配对，不因模型延迟、长句拆分或前端二次拆句错位。
- 尽量降低“视频已经到 24s，但右侧仍显示 20s 段落”的体感延迟和滚动失焦。

建议验收指标：

| 指标 | 目标值 |
| --- | --- |
| 播放开始到后端可接收音频 | <= 300ms |
| 前端播放时钟与已发送音频时钟偏差 | P95 <= 300ms |
| 新字幕输出后滚动到视野中心 | <= 200ms |
| 当前字幕卡片中心偏离容器中心 | <= 卡片高度的 0.5 倍 |
| 源文/译文 segment 配对错误 | 本地脚本化测试 0 例 |
| 2 分钟上传视频累计漂移 | <= 500ms |

## 当前问题判断

当前上传视频链路可以跑通，但不是高同步方案。

### 1. 上传视频存在双时钟

现在上传视频选择 `video-file` 后，前端创建后端会话并上传文件，视频使用浏览器本地 `blob:` 预览播放；后端则重新用 `ffmpeg` 解码上传文件，再按 1x 节奏喂给 LiveTranslate。

相关位置：

- `frontend/src/stores/session.ts`
  - `startConfiguredSession`
  - `connectSocket`
  - `playbackControlledSourceKeys`
- `frontend/src/components/workbench/MediaPanel.vue`
  - 视频播放、暂停、timeupdate 事件
- `backend/app/api/ws.py`
  - `upload_video` / `upload_audio` 分支
- `backend/app/services/pipeline.py`
  - `run_media`
- `backend/app/services/media.py`
  - `iter_pcm_frames`

这个设计的问题是：浏览器视频播放时钟和后端 `ffmpeg` 解码时钟是两个独立时钟。即使两边都按 1x 运行，也会因为 WebSocket 建连、LiveTranslate 连接、ffmpeg 启动、模型 VAD、网络返回延迟产生启动偏差和累计偏差。

### 2. 视频可能先播放，后端同传才真正开始

前端在上传视频模式里通过播放事件发送 `start_session`，但后端收到后还要连接同传引擎、启动 ffmpeg、开始喂音频。此时视频可能已经播放了若干秒。

结果就是字幕时间戳看似是 `00:20`，但真实输出已经发生在视频 `24s` 左右。

### 3. 上传视频没有维护 activeSegmentId

`syncFixturePlayback` 目前只对本地 fixture 做 `activeSegmentId` 计算。非 fixture 的上传视频只更新 `playbackMs` 后直接返回。

相关位置：

- `frontend/src/stores/session.ts`
  - `syncFixturePlayback`
  - `revealFixtureSegmentsUpTo`
  - `activeSegmentId`

因此上传视频模式下右侧字幕没有稳定的 active 卡片，滚动逻辑找不到 `[data-active='true']`，无法把对应字幕始终放在视野中心。

### 4. 右侧滚动策略不适合实时实验

`SentencePairView` 当前使用 `useStickyFollow(root, signature, { block: "start" })`，会把 active 卡片靠近顶部，而不是居中。并且 `useStickyFollow` 找不到 active 卡片时会直接返回，不会回退到最新字幕。

相关位置：

- `frontend/src/components/workbench/SentencePairView.vue`
- `frontend/src/composables/useStickyFollow.ts`

### 5. 源文和译文仍有错配风险

后端当前策略是：

- 源文按 `item_id` 归段。
- 译文按 `response_id` FIFO 绑定到最早未绑定译文的段。

相关位置：

- `backend/app/services/pipeline.py`
  - `_source_segment`
  - `_bind_response`
  - `_on_source`
  - `_on_translation`

方向正确，但仍是推断式绑定。如果模型事件中存在更明确的源输出关联字段，应该优先解析并使用。

前端还有一个额外风险：`transcriptPairs` 会把源文和译文分别拆句，再按 index 配对。长句、模型合并多句、源文和译文标点不一致时，会造成视觉上的源译错位。

相关位置：

- `frontend/src/stores/session.ts`
  - `transcriptPairs`
  - `splitDisplayText`
  - `splitLongText`

## 总体修正原则

同步率优先级从高到低：

1. 音频来源必须尽量和视频播放来源一致。
2. 字幕显示以“同一个 segment 的音频时间”为准，不以前端渲染时间猜测。
3. 右侧视图以“当前有效 segment”为中心，不只追底部。
4. 源文和译文必须先配对，再展示；不要展示层各自拆分后再按 index 猜配。
5. 暂不追求拖拽进度条后的上下文连续性；如果用户 seek，必须重置或标记断点，不能假装仍是同一段连续同传。

## 推荐最终方案：媒体元素采集作为上传视频唯一音频源

这是同步率最高的方案。上传视频播放时，不再让后端用 ffmpeg 重新解码同一个文件，而是从前端正在播放的 `<video>` / `<audio>` 元素直接采集音频，经 AudioContext 转为 16k PCM，通过 WebSocket 二进制帧推给后端。

链路变为：

```text
+---------------------+
| 浏览器 video/audio |
| 同一个播放时钟      |
+----------+----------+
           |
           | createMediaElementSource
           v
+---------------------+
| AudioContext 16kHz  |
| AudioWorklet PCM    |
+----------+----------+
           |
           | WS binary frame
           v
+---------------------+
| FastAPI run_pcm     |
| LiveTranslate       |
+----------+----------+
           |
           | transcript / translation / revision
           v
+---------------------+
| 前端字幕列表居中跟随 |
+---------------------+
```

收益：

- 视频画面、用户听到的音频、发给模型的音频来自同一个媒体元素。
- 播放、暂停天然同步；暂停时不再继续喂后端音频。
- 后端 `elapsed_ms` 可以由收到的 PCM 样本数计算，和前端播放时钟可持续对齐。
- 不需要依赖 ffmpeg 的 1x 节奏来模拟实时。

代价：

- 需要新增媒体元素音频采集能力。
- 上传视频时，后端不再靠上传文件解码实时音频；上传文件只用于存档、报告或备用。
- seek 需要明确处理：实验模式建议禁用 seek；如允许 seek，应重置当前同传会话或发送断点事件。

## 分阶段落地方案

### PR 1：修正启动握手，避免视频先跑

目标：即使暂时保留后端 ffmpeg 解码，也先解决启动偏差。

修改点：

| 文件 | 修改内容 |
| --- | --- |
| `frontend/src/stores/session.ts` | 上传视频/音频不应在 `modeStates.quick = running` 后立刻自动播放；应等待后端同传引擎 ready。 |
| `frontend/src/components/workbench/MediaPanel.vue` | 当上传视频处于 connecting/ready 前，阻止或暂停自动播放；收到 ready 后再播放。 |
| `backend/app/api/ws.py` | 为上传媒体增加 prepare/ready 阶段，后端连接 LiveTranslate 成功后发 `source_sync_state` ready 消息。 |
| `backend/app/services/pipeline.py` | 将“连接模型会话”和“开始喂音频”拆开，支持准备好后再启动。 |
| `frontend/src/types/events.ts` | 可扩展 `SourceSyncState.status`，增加 `ready`；或复用 `syncing` 并通过 message 表达 ready。 |

建议事件流程：

```text
前端创建 session
前端上传文件
前端连接 WS
前端发送 prepare_session
后端连接 LiveTranslate，准备 pipeline
后端发送 source_sync_state: ready
前端开始播放 video/audio
前端发送 start_session
后端开始喂音频
```

如果不新增 `prepare_session`，也可以在 WS open 后由前端发送 `start_session`，但前端视频必须保持暂停，直到后端发出“同传进行中 / ready”后再播放。

验收：

- 点击开始后，视频不会先于后端 ready 播放。
- 首帧音频喂入时间与视频 `play` 时间偏差 <= 300ms。

### PR 2：上传视频也维护 activeSegmentId，并让右侧居中跟随

目标：解决“没有把对应字幕始终放在右侧视野中心”的问题。

修改点：

| 文件 | 修改内容 |
| --- | --- |
| `frontend/src/stores/session.ts` | 将 `syncFixturePlayback` 改为通用 `syncPlayback`；非 fixture 也根据 `playbackMs` 和已有 segment 计算 `activeSegmentId`。 |
| `frontend/src/stores/session.ts` | 在收到 `transcript_segment` / `translation_segment` 时，如果该段是最新有效段，应更新 `activeSegmentId`。 |
| `frontend/src/components/workbench/SentencePairView.vue` | `useStickyFollow` 改为 `block: "center"`。 |
| `frontend/src/composables/useStickyFollow.ts` | 找不到 active 时回退滚动到最新卡片；active 卡片滚到容器中心。 |
| `frontend/src/App.test.ts` | 增加上传视频模式下 active segment 和居中跟随测试。 |

建议 active 计算：

```text
displayClockMs = playbackMs - estimatedOutputLatencyMs
active = segment where startMs <= displayClockMs < endMs
fallback = latest segment whose startMs <= displayClockMs
fallback again = latest available segment
```

说明：

- `estimatedOutputLatencyMs` 初始可用 1500ms。
- 真实链路可动态估算：字幕事件到达时记录 `arrivalPlaybackMs - segment.startMs`，取最近若干段中位数作为 `estimatedOutputLatencyMs`。
- 这样既能贴近真实同传延迟，又能保证右侧始终跟着当前可见字幕。

滚动策略：

```text
active card 存在 -> 居中滚动 active
active card 不存在 -> 居中滚动最新卡片
用户主动滚动 -> 暂停自动跟随，显示“回到最新”
点击回到最新 -> 恢复自动跟随并居中
```

验收：

- 上传视频实时输出时，最新/当前字幕卡片保持在右侧中部。
- 用户不手动滚动时，字幕更新后 200ms 内完成跟随。
- 用户手动滚动后，不强行抢滚；点击“回到最新”恢复。

### PR 3：媒体元素音频采集，替代上传视频后端 ffmpeg 实时解码

目标：让上传视频使用同一个播放时钟，最大化同步率。

修改点：

| 文件 | 修改内容 |
| --- | --- |
| `frontend/src/composables/useAudioCapture.ts` | 新增 `startMediaElementAudioCapture(element, options)`，支持从 `<video>` / `<audio>` 采集 16k PCM。 |
| `frontend/src/components/workbench/MediaPanel.vue` | 媒体元素 mounted / loadedmetadata 后向 store 暴露当前 media element；播放时启动采集，暂停时暂停采集。 |
| `frontend/src/stores/session.ts` | `video-file` / `audio-file` 改走 PCM 推流模式，而不是依赖后端 `upload_video` / `upload_audio` 解码实时音频。 |
| `backend/app/api/sessions.py` | 可新增 `media_element_audio` inputMode；也可以复用现有采集类 inputMode，但建议新增明确模式。 |
| `backend/app/api/ws.py` | 将 `media_element_audio` 归入 `CLIENT_CAPTURE_MODES`，走 `run_pcm_stream`。 |
| `backend/app/services/pipeline.py` | 继续使用 `run_pcm_stream`，并支持前端上报 media clock 用于 lag 监控。 |
| `frontend/src/types/events.ts` | 可增加 `media_clock` 客户端事件类型约定，或仅在 WS 层内部发送 JSON。 |

建议新增前端采集函数：

```ts
startMediaElementAudioCapture(element, {
  onChunk,
  onClock,
  sampleRate: 16000,
  frameMs: 80
})
```

实现要点：

- 使用 `AudioContext({ sampleRate: 16000 })`。
- 使用 `createMediaElementSource(element)` 获取正在播放的音频。
- 音频源同时连到 `context.destination`，保证用户仍能听到声音。
- 另一路连到 AudioWorklet，将 Float32 转为 s16le PCM。
- 每 60-100ms 发一帧；为了更低延迟，建议上传视频实验先用 80ms。
- 每 500ms 上报一次 `media_clock`：`playbackMs`、`sentAudioMs`、`bufferedMs`。

后端处理：

```text
收到二进制 PCM -> pipeline.run_pcm_stream
按 PCM 字节数更新 elapsed_ms
收到 media_clock -> 计算 lagMs = playbackMs - elapsed_ms
通过 source_sync_state 回传同步状态
```

验收：

- 暂停视频后，后端不再继续收到音频帧。
- 恢复播放后，音频帧继续与视频进度一致。
- 2 分钟内 `playbackMs - sentAudioMs` P95 <= 300ms。

### PR 4：修正源文/译文配对和展示拆分

目标：解决源文、译文、视频音频对应性问题。

后端修改点：

| 文件 | 修改内容 |
| --- | --- |
| `backend/app/services/providers/dashscope/realtime.py` | 保留 raw 事件里的关联字段，优先解析可用的源 item / response 关系。 |
| `backend/app/services/pipeline.py` | `_bind_response` 从纯 FIFO 升级为“明确关联优先，FIFO 兜底”。 |
| `backend/app/services/session_store.py` | `SegmentRecord` 可增加 `audio_start_ms`、`audio_end_ms`、`response_created_ms`、`first_emit_ms` 便于调试。 |
| `backend/tests/test_pipeline.py` | 增加乱序、长句、跨 speech_started、多个 response 并发的配对测试。 |

前端修改点：

| 文件 | 修改内容 |
| --- | --- |
| `frontend/src/stores/session.ts` | `transcriptPairs` 不再对源文和译文独立拆分后按 index 配对。 |
| `frontend/src/components/workbench/SentencePairCard.vue` | 一个模型 segment 对应一个卡片；长文本在卡片内部换行或折叠，不拆成多个独立 pair。 |
| `frontend/src/components/workbench/SentencePairView.vue` | 以 segmentId 作为稳定 key 和滚动目标。 |
| `frontend/src/App.test.ts` | 增加“源文比译文长 / 译文无标点 / 模型合并多句”不视觉错配的测试。 |

展示规则：

```text
同一个 segmentId:
  source_text
  translation_text
  status
  startMs/endMs
  revision info

长文本只在同一张卡片内分段显示，不生成新的 segmentId:index 卡片。
```

这样可以避免源文被拆成 2 块、译文被拆成 1 块时产生视觉错配。

### PR 5：seek 策略和实验限制

目标：避免用户拖动进度条后模型上下文和视频上下文不一致。

建议实验版采用严格策略：

- 同传运行中禁止 seek，或 seek 后弹出确认。
- 如果用户确认 seek：
  - 停止当前后端同传。
  - 清空当前实时 segment。
  - 以新的播放位置重新开始一个后端实时会话。
  - 报告中记录 discontinuity。

修改点：

| 文件 | 修改内容 |
| --- | --- |
| `frontend/src/components/workbench/MediaPanel.vue` | 监听 `seeking` / `seeked`，运行中阻止或确认重启。 |
| `frontend/src/stores/session.ts` | 增加 `handleMediaSeeking` / `restartFromCurrentPlayback`。 |
| `backend/app/api/ws.py` | 如支持同一 session 断点，可增加 `reset_stream`；否则创建新 session 更简单。 |
| `backend/app/services/report.py` | 报告里记录断点，避免会后文本误认为连续上下文。 |

## 推荐优先级

建议按以下顺序实施：

1. PR 1：启动握手，防止视频先跑。
2. PR 2：active segment + 居中跟随，先把实验观感修好。
3. PR 3：媒体元素采集，解决上传视频双时钟，这是同步率提升最大的改动。
4. PR 4：源译配对和前端展示拆分，提升准确性和稳定性。
5. PR 5：seek 策略，避免实验过程产生不可解释的错位。

如果时间很紧，最小可交付版本是 PR 1 + PR 2。  
如果目标是“同步率越高越好”，必须做 PR 3。

## 同步率观测方案

为了证明修正有效，建议加一个轻量调试面板或日志。

前端每 500ms 采集：

```text
playbackMs: video.currentTime * 1000
sentAudioMs: 已发送 PCM 样本数 / 16000 * 1000
lastSegmentStartMs
lastSegmentArrivalPlaybackMs
estimatedOutputLatencyMs
```

后端每次 `source_sync_state` 输出：

```text
elapsedMs: 后端累计收到/喂入 PCM 的音频时长
clientPlaybackMs: 最近一次前端上报播放时间
lagMs: clientPlaybackMs - elapsedMs
```

前端展示可先不暴露给用户，但测试时应能从 console 或日志中看到：

```text
[sync] playback=24020ms sentAudio=23880ms backendElapsed=23800ms lag=220ms outputLatency=1650ms active=seg-008
```

## 验收用例

### 用例 1：普通上传视频播放

步骤：

1. 选择视频文件。
2. 点击开始同传。
3. 等待后端 ready。
4. 视频自动播放。
5. 观察右侧字幕。

期望：

- 视频不会在后端 ready 前提前播放。
- 字幕输出后自动居中到右侧视野。
- `source_sync_state.lagMs` 稳定在 300ms 内。

### 用例 2：视频 20-24s 段落

步骤：

1. 播放到 20-24s。
2. 观察“trash / neighbor / value”相关段落。

期望：

- 如果模型把 19s、22s、24s 合并为一个 segment，右侧显示为同一张长卡片，不拆错源译。
- 该 segment 输出时自动居中。
- 卡片时间显示应体现音频段起点，同时可显示“输出延迟约 Xs”用于调试。

### 用例 3：暂停与恢复

步骤：

1. 播放过程中暂停视频 5s。
2. 恢复播放。

期望：

- 暂停期间前端不继续发送 PCM。
- 后端 `elapsed_ms` 不继续增长。
- 恢复后字幕继续跟随当前视频。

### 用例 4：用户手动滚动右侧字幕

步骤：

1. 同传运行中手动滚动右侧字幕到历史段。
2. 等待新字幕输出。
3. 点击“回到最新”。

期望：

- 用户手动滚动后不强制抢回。
- “回到最新”点击后恢复居中跟随。

### 用例 5：seek

实验版建议：

- 运行中 seek 被阻止或提示重启。

如允许 seek：

- seek 后当前同传会话重置。
- 报告中标记断点。
- 不把 seek 前后的文本混为连续上下文。

## 风险与取舍

### 模型天然延迟无法完全消除

同传模型需要 VAD、识别、翻译、返回事件。即使用同一个音频源，也会有 1-3s 的输出延迟。优化目标不是让字幕零延迟，而是：

- 音频输入和视频播放不漂移。
- 输出延迟稳定、可估算。
- 当前输出字幕始终可见且居中。

### seek 无法保持上下文连续

用户跳到新时间点后，模型的上下文仍来自旧时间段。为了保证实验结果可信，seek 必须重置会话或显式记录断点。

### 后端 ffmpeg 路径仍有价值

URL、demo、批量压测仍适合后端 ffmpeg 解码。只是上传视频实时实验为了最高同步率，应优先走媒体元素采集。

## 最终建议

如果目标是“尽快提升实验观感”，先做：

```text
PR 1 启动握手
PR 2 active 字幕居中跟随
```

如果目标是“输出同步率越高越好”，必须做：

```text
PR 3 上传视频改为媒体元素音频采集
```

最终推荐主链路：

```text
上传视频文件
前端 video 播放
从 video 元素采集音频
WS 发送 16k PCM
后端 run_pcm_stream
模型输出 segment
前端按 segmentId 配对展示
active segment 居中跟随
media_clock 持续校准 lag
```

这条链路能把“视频播放”和“模型输入”收敛到同一个时钟源，是上传视频实时同步实验最稳的方案。
