一、本轮已确认的四项决策
================================================================
1) 前端框架：Vue 3 + Pinia；后端语言：Python (FastAPI)（均按团队熟悉度确认）
2) 平台重心：Web 优先；桌面端（Tauri）轻投入，作为 P2 加分项
3) 可用 AI Key：OpenAI 体系 / 国外专业流式 ASR(Azure·Deepgram) / 国内厂商
                (火山豆包·讯飞) / Claude·DeepSeek —— 四类齐全，可按能力择优
4) 仓库形态：单题单仓（frontend/ + backend/ + 可选 desktop/）

影响：

· Key 齐全 → 可定"主链路 + 备选"，并真实演示多供应商热切换（创新点 5）。

二、最终技术栈总表
================================================================
【前端】
  语言/框架      TypeScript + Vue 3（Composition API）+ Vite
  样式           Tailwind CSS
  状态管理       Pinia（Vue 官方；细粒度响应式天然适合字幕高频原地更新、三态切换不卡顿）
  音频采集       Web Audio API + AudioWorklet（取 PCM，48k→16k 重采样）

  目标浏览器     Chrome（标签页/系统音频共享支持最好）

【后端】
  语言/框架      Python 3.11 + FastAPI
  ASGI 服务      uvicorn[standard]
  实时通道       WebSocket（音频上行二进制 16k PCM 帧；事件下行 JSON）
  数据校验       Pydantic v2
  统一 AI 接入层 自研 Provider Gateway（能力接口 + 适配器 + 路由/降级）
  端点检测(VAD)  Silero VAD（本地、低延迟，用于语义分块）
  存储           SQLite + SQLModel（会话/字幕/术语表，零运维）
  HTTP 客户端    httpx（异步调用各云端供应商）

【桌面端 · P2 加分项（后置）】
  外壳           Tauri 2（Rust，复用同一前端）
  系统音频       Rust cpal（loopback）—— 视演示需要再做，不阻塞主线

【工程质量】
  包管理         pnpm（前端）/ uv（Python，快）
  Lint·格式      ESLint + Prettier（TS）/ ruff + black（Python）
  测试           vitest（前端）/ pytest + pytest-asyncio（后端）
  CI             GitHub Actions（lint + test + build，保证主分支可运行）
  配置           .env（密钥，不入库）+ providers.yaml（路由/降级策略）

★ 两层翻译设计（贴合"延迟 vs 准确"主题，强烈建议）
  - 临时态译文：用"快而便宜"的模型抢跑（高频、低延迟）；
  - 稳定/已修正态：用"强模型"做带上下文的回溯修正与术语一致性（低频、高质量）。
  这样既保证实时性，又让"修正"确有质量提升，与三态字幕天然契合。

★ P0 先接哪条（减少决策成本）
  最快出第一条通路：用 OpenAI 一家把"流式转写 + 翻译"跑通（单 SDK、单 Key）；
  随后接入 Deepgram(ASR) 与 Claude(翻译/修正) 作为备选，既提质量又演示热切换。

四、音频采集方案（Web 优先，按"演示稳定性"排序）
================================================================
方案 A（最稳，演示首选）：内置播放器 + MediaElementSource
  应用内放一段视频/音频，用 Web Audio 的 MediaElementSource 直接取音频，
  无需 getDisplayMedia 授权弹窗，demo 最可控、最不易翻车。
方案 B（真实场景）：getDisplayMedia({audio:true}) 抓"标签页/窗口"音频
  共享某个标签页并勾选"共享音频"，适配看任意网页视频/在线会议。
方案 C（兜底）：麦克风/外放采集（质量差，仅作 fallback）
方案 D（P2，桌面端）：Tauri + 系统 loopback，抓"系统正在播放的任意声音"
统一处理：任一来源 → AudioWorklet 取 Float32 → 降采样 16k 单声道 →
          Int16 PCM 二进制帧经 WebSocket 上行。

五、关键选型理由（备答辩/README）
================================================================
· Python 后端：本地 faster-whisper / Silero VAD 兜底最顺，asyncio 流式成熟，
  各家供应商 SDK 最全；契合"多家可切换 + 现场不翻车"。
· WebSocket 而非 WebRTC：本场景是"单向捕获→服务端"，WebSocket 足够且更简单；
  WebRTC 留作未来超低延迟优化。
· Vue 3 + Pinia：字幕是大量小片段的高频增量更新，Vue 细粒度响应式直接追踪依赖、
  原地更新对应片段，免去 React 里手动 memo 防重渲染的样板，三态切换更顺手。
· Silero VAD（本地）：端点检测放本地，零网络延迟，是"语义分块/延迟预算"的基础。
· 两层翻译 + 三态字幕：把"延迟 vs 准确"的取舍落到工程上，是创新点的落地形态。
· 单题单仓：只做本题，结构最简、PR 最聚焦，利于"持续小步提交 + 主分支可运行"。
