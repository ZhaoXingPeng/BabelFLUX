一、一句话价值主张
================================================================
看英文演讲 / 网课 / 国际会议时，提供一条“边听边译、还会自我纠错、术语前后
一致”的实时中文字幕——把同声传译里“延迟 vs 准确”的取舍交给系统去动态处理，
并让用户亲眼看到它在自我修正。

核心定位：不是又一个“逐句翻译字幕”，而是一个把“修正”做成一等公民的实时同传系统。

================================================================
二、目标用户与典型场景
================================================================
目标用户：英语听力跟不上但需要获取英文音视频信息的人——学生（网课/公开课）、
          技术从业者（技术分享/发布会）、研究者（国际会议/讲座）、职场人（跨国会议）。

典型场景：
  S1 看 YouTube/B站 上的英文技术演讲或公开课（单向、可回放）
  S2 实时参加英文线上会议/网络研讨会（单向收听，强实时）
  S3 看无中文字幕的英文视频/纪录片
共同特征：单向音频流（听别人讲，自己不需要被翻译回去）、需要“跟上节奏”、
          内容含专有名词/人名/术语、说话有口音和口语化停顿。

================================================================
三、问题分析：为什么这件事不简单（创新的前提）
================================================================
3.1 同声传译的本质矛盾：延迟 vs 准确
    要“同步”，就必须在一句话说完之前就开始翻译；但话没说完，上下文不全，
    早翻往往会错（指代不清、歧义、花园小径句、专名未确认）。
    人类同传译员靠“预测 + 自我修正”来化解这个矛盾——这恰恰是机器要学的。

3.2 现有工具的普遍做法与不足（据常见产品形态归纳，作为定位参照）
    多数实时翻译/字幕工具（直播自动字幕、会议实时翻译、翻译App的转写模式等）
    存在以下共性短板：
    (a) 逐句独立翻译、缺乏跨句上下文 → 指代、时态、专名前后不一致；
    (b) 译文一旦显示就“定稿”，不会回头修正 → 早期的错误永远留在屏幕上；
    (c) 术语漂移：同一个人名/术语，全程被翻成好几种叫法；
    (d) 字幕抖动：逐词刷新、跳来跳去，可读性差；
    (e) 延迟/准确是写死的，用户无法按场景调整；
    (f) 音频来源受限：纯网页工具难以稳定抓取“系统正在播放的声音”。

3.3 官方要求的“题眼”
    本题明确要求：“系统需具备修正能力，能够自动纠正之前识别或翻译的错误。”
    → 大多数同类方案恰恰最弱的就是这一点。把“修正”做深、做实、做得可见，
      既是差异化创新，又是直接命中题目要求，是本项目的战略重心。

================================================================
四、产品形态与核心功能
================================================================
形态：Web 应用为主（快速出 demo）+ 桌面端 Tauri 备选（解决系统音频采集）。
      两者复用同一前端与同一后端实时管线。

核心功能：
  F1 多来源音频接入：网页抓“标签页/窗口音频”；桌面抓“系统播放音频”；麦克风兜底。
  F2 实时双语字幕：上行原文（英），下行中文，随讲滚动。
  F3 三态可修正字幕：临时 / 稳定 / 已修正三态可视区分（见六）。
  F4 自动修正：识别修正 + 翻译回溯修正 + 术语全局一致（见五、六）。
  F5 延迟-准确度调节：快速 / 平衡 / 准确 三档（或滑块）。
  F6 术语包：可加载领域术语（如 AI/医学/法律），并自学习演讲中的专名。
  F7 历史与导出：整场可回看、可搜索、导出双语 srt/txt。
  F8 中文配音（可选、弱优先）：朗读“稳定态”句子，做画外音式辅助。

================================================================
五、创新点到底在哪里（本文件重点）
================================================================
■ 创新主线（一句话）
  市面工具把“翻译”当作一次性、逐句、无上下文、不可回改的动作；
  而真正的同传是一个“边猜边修”的连续过程。
  本项目的核心创新 = 把“修正”从一个隐形、偶发的后端行为，
  提升为产品的一等公民：可见、可信、多层、全场贯穿。

下面 6 个创新点，前 4 个是产品/算法层，后 2 个是工程/平台层。
每个都按【是什么 / 解决什么 / 为什么难(护城河) / 如何演示】说明。

----------------------------------------------------------------
创新点 1：三态可修正字幕（让“自我纠错”可见、可信）
----------------------------------------------------------------
是什么：每段译文有稳定身份与生命周期，肉眼可分三态——
        · 临时态(tentative)：灰/斜体，基于不完整信息的“抢跑”翻译，随时会变；
        · 稳定态(stable)：正常显示，信息足够、已确认；
        · 已修正态(revised)：带轻微高亮/划改动画，之前显示过、现已被纠正。
解决什么：现有工具要么不纠错，要么“偷偷改”让人困惑。三态把“系统在自我纠错”
        变成可感知、可信任的体验——用户知道哪些能立刻信、哪些还会变。
为什么难（护城河）：不是改个字体颜色那么简单。需要：①给每个译文片段稳定 id；
        ②把流式 ASR 的 partial/final 与“翻译单元”对齐；③原地平滑替换而非整屏重刷；
        ④用滞后/置信阈值(hysteresis)决定“何时提交、何时回改”，避免字幕乱跳。
        这是状态管理 + 交互设计的系统工程，不是一句 prompt。
如何演示：一句话先出灰色临时译文 → 听完后变正常并修正用词，镜头感强。

----------------------------------------------------------------
创新点 2：增量翻译 + 回溯修正引擎（低延迟下保正确）
----------------------------------------------------------------
是什么：不等整句说完就按“语义块”抢先翻译（低延迟）；同时维护最近 K 句的
        上下文窗口，当后文到来揭示前文译错（指代被确定、歧义被消除、花园小径句
        被拆解）时，对“前文+新句”联合重译并回填更新前面的字幕。
解决什么：直接命中“延迟 vs 准确”的根本矛盾，也直接满足官方“自动纠正之前
        翻译错误”的要求。
为什么难（护城河）：难点不在“翻得准”（大模型本就强），而在流式编排：
        ①翻译单元怎么切（VAD + 标点/边界预测找子句边界）；②延迟上限怎么兜
        （最大等待阈值，超时强制出译文）；③什么时候值得回改（只在置信度实质提升
        时改，否则忍住，避免闪烁）；④回改要便宜（只重译受影响的最小范围）。
        这是“何时翻、何时改”的决策策略，是真正的工程壁垒。
如何演示：放一段含歧义/长难句的演讲，展示前句译文随后文出现而被修正。

----------------------------------------------------------------
创新点 3：术语自学习 + 全局回填（解决“专名前后不一致”）
----------------------------------------------------------------
是什么：流式识别专有名词/人名/术语/缩写；一旦确定其规范译名，把此前所有
        出现处统一回填，并锁定后续译法。也支持用户预载“领域术语包”。
解决什么：长演讲里“同一个名字被翻成五种叫法”“专名先听错后没人改”的顽疾。
为什么难（护城河）：流式文本上的实体识别 + 规范形确定 + 对“已显示字幕”的
        追溯式一致编辑 + 与回溯修正引擎协同，避免改了这处漏了那处。
如何演示（最强镜头）：演讲者名字一开始被译错，后文再次出现时，系统自动把
        前面所有出现处一次性更正为统一译名——观众能直观看到“全局自我纠错”。

----------------------------------------------------------------
创新点 4：延迟-准确度可调（把同传的核心取舍交给用户）
----------------------------------------------------------------
是什么：用“快速 / 平衡 / 准确”三档（或滑块）调节语义块大小与最大等待阈值，
        在“更快更碎”和“更稳更整”之间移动。
解决什么：不同场景诉求不同——闲聊型内容要快，技术讲座要稳。没有放之四海皆准
        的单点，把取舍显式交给用户是更诚实、更实用的产品设计。
为什么有价值：它是对“延迟 vs 准确”这一本质矛盾的产品化表达，体现了我们对
        问题本质的理解，而非回避。
如何演示：同一段音频，拖动滑块对比“快档抢跑多、改得多”与“准档稳但略慢”。

----------------------------------------------------------------
创新点 5：多供应商可热切换的统一 AI 接入层（工程创新）
----------------------------------------------------------------
是什么：ASR / 翻译 等能力抽象为统一接口，按语种/领域/延迟/可用性路由到最优
        供应商，支持热切换与故障降级（如云端 ASR 超时 → 本地 whisper 兜底）。
解决什么：规避单点故障与网络/合规风险；按能力取各家所长；保证 demo 不因某家
        抽风而翻车。
为什么有价值：实时系统最怕“现场掉链子”，可切换+可降级是稳定性的工程保障，
        也是“架构清晰度/健壮性”评分的加分项。

----------------------------------------------------------------
创新点 6：Web + 桌面双形态系统音频采集（平台创新）
----------------------------------------------------------------
是什么：Web 端抓标签页音频快速可用；桌面端（Tauri）用系统 loopback 直接采集
        “电脑正在播放的任意声音”。
解决什么：纯网页工具难以稳定抓系统音频，而“看视频/开会”恰恰需要它。桌面端
        让产品贴合真实使用场景。
为什么有价值：补齐了同类网页工具的关键体验短板，扩大可用场景。

----------------------------------------------------------------
★ 直面质疑：“这不就是调个翻译 API 吗？”——创新的护城河
----------------------------------------------------------------
翻译质量本身已是大模型的“水电煤”，不构成壁垒。本项目的难点与价值，全部在
“把一次性翻译”改造成“流式、有状态、会自我修正的连续过程”所需要的系统工程：
  · 语义分块与延迟预算（何时该翻）
  · 片段稳定身份与 partial/final 对齐（怎么持续更新而不乱）
  · 提交/回改的决策策略与滞后阈值（何时该改、何时该忍，防闪烁）
  · 术语一致性的追溯式编辑（全局回填）
  · 让修正“可见且可信”的交互设计（三态字幕）
  · 多供应商可切换与降级（现场不翻车）
一句话：“能翻译” ≠ “能做好流式同传”。我们做的是后者。

================================================================
六、核心技术原理（讲清“修正”如何发生，概念层，不含代码）
================================================================
6.1 三层修正模型（按错误类型分层兜底）
    把“修正能力”拆成三层，各修一类错误，合起来覆盖错误全谱系：
    L1 识别层修正：流式 ASR 的 partial→final。随更多音频到达，识别假设被修订。
                   我们把基于 partial 的译文标“临时态”，final 到达即纠正。
                   （修正对象：听错）
    L2 翻译层回溯修正：即便识别正确，早翻的子句也可能因上下文不全而译错。
                   维护上下文窗口，新句揭示前句有误时联合重译、回填。
                   （修正对象：误解 / 抢跑导致的错译）—— 创新点 2 的机制
    L3 一致性层修正：术语/人名一旦确定规范译法，全场回填统一、后续锁定。
                   （修正对象：前后不一致）—— 创新点 3 的机制

6.2 语义分块（延迟控制的关键）
    用 VAD（端点检测）+ 标点/子句边界预测，找“可翻译的最小语义单元”；
    设最大等待阈值，超时即强制出译文，给延迟设上限。
    “延迟-准确度”档位 = 调节块大小与该阈值。

6.3 三态字幕生命周期（修正的 UX 呈现）
    片段创建→临时态(基于 partial/抢跑) →（信息足够）稳定态
    →（被 L2/L3 触发）已修正态（平滑高亮替换）。
    关键策略：只有当新结果置信度“实质优于”当前显示时才回改，避免抖动。

6.4 端到端数据流（文字版）
    音频源 →[采集/重采样]→ 流式ASR(partial/final)
          →[语义分块]→ 增量翻译(LLM/MT, 带上下文窗口)
          →[三态字幕渲染 + 术语回填]→ 屏幕
          （上下文窗口 & 术语表持续驱动 L2/L3 修正）
          →（可选）中文TTS朗读稳定句

6.5 片段数据模型（概念，非最终字段）
    segment{ id, t_start, t_end, asr_text, asr_state(partial|final),
             zh_text, zh_state(tentative|stable|revised),
             revised_from, confidence }
    字幕区 = 这些 segment 的实时投影；导出 = 按时间轴拼接。

================================================================
七、系统总体架构（模块职责，概念层）
================================================================
（复用《总览》的“统一 AI 接入层”，此处只列本项目模块与职责）
  · 音频接入层：Web(标签页音频)/桌面(系统loopback)/麦克风 → 统一 PCM 流
  · 实时网关(后端 WebSocket)：音频上行、事件下行，编排管线
  · ASR 适配（经统一接入层）：输出 partial/final + 时间戳 + 置信度
  · 语义分块器：决定翻译单元与延迟预算
  · 增量翻译 + 回溯修正引擎：上下文窗口、提交/回改决策（L2）
  · 术语一致性服务：实体识别、规范译名、全局回填（L3）
  · 字幕状态机：维护片段身份与三态、向前端推增量更新
  · 前端字幕 UI：三态渲染、平滑更新、历史/导出、档位与配音控制
  · 配置：providers.yaml（路由/降级）、术语包

================================================================
八、关键设计决策与权衡
================================================================
D1 字幕优先、配音次要：语音覆盖语音体验差且难，v1 以双语字幕为主，
   配音作为可选辅助（仅朗读稳定句、可降低原声音量）。
D2 英→中优先：先把英译中做扎实，架构预留多语言（其他外语为后续）。
D3 “敢抢跑、肯回改”而非“等整句”：宁可先出临时译文再修，也不牺牲实时性；
   用三态 + 滞后阈值控制由此带来的抖动。
D4 修正要“可见”而非“偷改”：把纠错暴露给用户是信任来源，也是 demo 卖点。
D5 一切实时能力走统一流式协议：换供应商对上层零改动（来自《总览》接入层）。

================================================================
九、范围边界（v1 做什么 / 不做什么）
================================================================
v1 做：
  · 单向音频 → 实时中文字幕（英→中）
  · 三层修正（L1/L2/L3）+ 三态字幕
  · Web(标签页音频) + 桌面(系统音频)
  · 延迟-准确度档位、术语包、历史/导出
v1 不做（后续/明确排除）：
  · 双向对话式翻译（那是题目一方向，避免与本题混淆）
  · 多说话人分离与标注(diarization)（v1 不做或仅最简）
  · 高保真中文配音覆盖原声（v1 字幕优先，配音为弱辅助）
  · 自训练/本地大模型微调（仅用现成能力 + 本地 whisper 兜底）

================================================================
十、成功指标与可量化评估（体现工程严谨，也利于 demo 讲数据）
================================================================
延迟类：
  · 首字延迟、整句稳定延迟（平衡档目标约 2~4s，可跟读）
准确/修正类：
  · 修正带来的准确率提升：最终字幕 vs 仅用 partial 不回改的字幕，BLEU/人工对比
  · 术语一致性率：指定术语全程被一致翻译的比例（目标显著高于逐句基线）
可读性/稳定性：
  · 字幕跳变次数（flicker）：越低越好（验证滞后阈值有效）
鲁棒性：
  · 供应商故障时的降级成功率与切换耗时
评估方式：选 2~3 段公开英文演讲做固定评测集，跑“逐句基线 vs 本系统”对比，
         用数据证明“修正”确有价值（既验证设计，也产出 demo/README 素材）。

================================================================
十一、风险与应对
================================================================
· 浏览器系统音频受限 → 桌面端 loopback 兜底（这正是要桌面备选的原因）
· ASR 断流/网络抖动 → 心跳 + 断线重连 + 本地 whisper 兜底
· 回溯修正导致字幕乱跳 → 滞后/置信阈值，仅在实质改善时回改 + 平滑动画
· 延迟过高跟不上 → 最大等待阈值 + 低延迟档 + 临时态先出
· 中文配音盖过原声 → 默认关；开启时降低原声音量/仅朗读稳定句
· 三天做不完 → 分层交付（见下）

================================================================
十二、与评审维度的对应（自检表）
================================================================
完整度&创新 40%：
  · 完整：P0 即是可用产品；P1/P2 逐层加分（见“后续规划”分层）
